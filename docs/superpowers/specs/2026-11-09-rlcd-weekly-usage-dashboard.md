## Problem Statement

The owner wants to glance at their Waveshare ESP32-S3-RLCD-4.2 and see how much weekly subscription allowance remains for Claude, Codex, Kimi, and Gemini. The device currently runs the offline desk-climate dashboard. The public token heatmap on justinyan.app reports merged daily token totals, which cannot determine subscription-limit percentages.

The M4 Mac already runs a customized OpenUsage application with valid weekly snapshots for all four services. Its current supported integration is a read-only CLI exporting cached data. Just Ship already accepts authenticated uploads from the Macs and serves an HTTPS API through a Cloudflare Worker backed by D1. The feature should reuse those working boundaries and make stale or unavailable data unmistakable.

## Solution

Add a weekly usage dashboard to the RLCD, backed by a small authenticated API on the existing justinyan.app Worker. A separate M4 scheduled uploader reads OpenUsage's cached weekly snapshots every five minutes and sends only the four selected resources. D1 retains each provider's latest valid snapshot.

The RLCD shows four rows with provider name, remaining percentage, used percentage, a remaining-allowance bar, and freshness/reset information. Gemini explicitly means the Antigravity Gemini weekly pool. The dashboard is the configured device's startup view, while the existing climate Dashboard remains accessible through the current buttons.

When the M4, a provider, or the network stops updating, the device retains the last successful values and marks them stale. A provider without any valid weekly snapshot displays unavailable, never a fabricated 0% used or 100% remaining.

The accepted architecture is M4 OpenUsage → scheduled uploader → existing Cloudflare Worker and D1 → RLCD over HTTPS. No Cloudflare Tunnel or new HTTP origin is required.

## User Stories

1. As an RLCD owner, I want one dashboard showing all four providers, so that I can assess available coding capacity at a glance.
2. As an RLCD owner, I want remaining allowance to be the primary percentage, so that I can quickly decide which provider to use.
3. As an RLCD owner, I want the used percentage alongside the remaining percentage, so that I can understand both sides of the weekly limit.
4. As an RLCD owner, I want each bar to represent remaining allowance consistently, so that a fuller bar always means more capacity.
5. As a Claude subscriber, I want the account-wide weekly limit, so that a model-specific limit is not mistaken for my overall allowance.
6. As a Codex subscriber, I want the normal weekly limit, so that Spark, session limits, credits, and reset credits do not change the meaning of the dashboard.
7. As a Kimi subscriber, I want the reported weekly limit, so that I can use my existing subscription data without configuring another collector.
8. As an Antigravity user, I want the Gemini row identified as Antigravity's Gemini weekly pool, so that it cannot be confused with Gemini CLI or another Google product.
9. As a user with multiple accounts, I want explicit selection of the account for each provider, so that unrelated account percentages are never combined or selected arbitrarily.
10. As an RLCD owner, I want source sampling time or age to be visible, so that I know how current the displayed values are.
11. As an RLCD owner, I want expired snapshots clearly marked, so that an HTTP success cannot make old provider data appear fresh.
12. As an RLCD owner, I want an unavailable provider shown as unknown, so that missing data never looks like a full allowance.
13. As an RLCD owner, I want the last valid values retained during a fetch failure, so that temporary outages do not erase useful information.
14. As an RLCD owner, I want stale markers to advance while the network is unavailable, so that a retained screen does not claim indefinite freshness.
15. As an RLCD owner, I want cached usage restored after restart, so that the dashboard remains useful before the next successful fetch.
16. As an RLCD owner, I want weekly resets handled using the provider's reset time, so that the screen does not assume a Monday-to-Sunday calendar week.
17. As an RLCD owner, I want a newer post-reset snapshot accepted even when usage drops, so that renewed allowance appears correctly.
18. As an RLCD owner connected to a USB data host, I want five-minute polling, so that the dashboard keeps up with the scheduled source updates.
19. As an RLCD owner using battery power, I want the existing ECO and wake behavior retained, so that the new feature does not silently replace the power policy.
20. As an RLCD owner, I want to return to the climate Dashboard with the existing buttons, so that I keep temperature, humidity, and battery information.
21. As an RLCD owner, I want the usage page selected at startup on this configured device, so that the requested information is immediately visible.
22. As the M4 operator, I want the uploader to read OpenUsage's cache without refreshing credentials or signing in, so that collection does not disturb my coding tools.
23. As the M4 operator, I want the new uploader scheduled independently of daily token collection, so that five-minute allowance updates do not repeatedly scan historical logs.
24. As the M4 operator, I want failed or overlapping runs bounded and diagnosed, so that the job cannot create a retry storm or pretend collection succeeded.
25. As the site owner, I want existing token heatmap behavior preserved, so that adding device data does not change the website's public contract.
26. As the account owner, I want only selected allowance metrics uploaded, so that emails, provider credentials, prompts, and unrelated balances remain private.
27. As the device owner, I want a read-only device credential, so that the RLCD cannot alter uploaded data or the existing token totals.
28. As the service operator, I want repeated and out-of-order uploads handled safely, so that retries cannot overwrite newer observations or inflate writes unnecessarily.
29. As the service operator, I want bounded storage and measurable database activity, so that the feature fits the existing Workers Paid plan predictably.
30. As the maintainer, I want staged deployment and a simple rollback, so that failures in the new feature do not require destructive changes to the existing site or device data.

## Implementation Decisions

- **Repository ownership:** Just Ship owns the M4 uploader, scheduling, normalization, Worker API, and D1 storage. rcink owns the RLCD HTTP consumer, cached usage state, rendering, and device integration. OpenUsage continues owning provider authentication, refresh, account selection metadata, and source cache; no OpenUsage changes are needed for this scope.
- **Domain boundaries:** Daily Token Usage Totals remain source-scoped, additive activity data. Weekly Allowance Snapshots are account-scoped observations and must not be summed across machines or accounts. Preserve the existing public-heatmap privacy boundary, authenticated-write contract, and local-collector boundary established by Just Ship's ADRs.
- **Source contract:** Consume only `openusage.limits.v2` from the read-only helper bundled with the M4's running OpenUsage application. Resolve its configured absolute location rather than trusting an unrelated executable on PATH. The running application must continue its existing refresh schedule; exporting its cache does not refresh it or launch the application.
- **Provider mapping:** Use the configured stable account ID for each slot. Map Claude, Codex, and Kimi to `weekly`; map the Gemini slot to Antigravity's `geminiWeekly`. Require consumption/percent semantics, a positive finite limit, nonnegative finite usage, and a 604800-second window. Do not substitute session, monthly, model-scoped, non-Gemini, or balance resources. Missing or ambiguous configuration must produce a clear collection diagnostic rather than guessing an account.
- **Normalization:** Derive used percentage from used/limit, clamp the normalized display range to 0–100, and derive remaining as its complement. Retain precision in the API; on the display, round used once and derive the displayed remaining integer from it. Do not use OpenUsage's export time as provider sampling time. Convert source timestamps into validated UTC epoch seconds; preserve optional reset times as null when absent.
- **M4 cadence:** Add one independent launchd job that runs on login and every 300 seconds under the owning user's session. Reuse the existing Node runtime, fetch support, and collector conventions. Bound helper execution and HTTP timeouts; prevent overlapping runs. A failed run exits with a useful sanitized diagnostic and retries on a later schedule, without an unbounded immediate retry loop. Keep the daily ccusage collector and its completion gate unchanged.
- **Upload boundary:** Add authenticated `PUT /api/usage-limits` to the existing Worker. Reuse `X-Usage-Api-Key` and its current/previous key validation. The exact JSON envelope contains `schema`, `sourceId`, and `providers`; schema is `rcink.usage-limits.v1`, source is the configured M4 source, and providers contains one to four unique items. Each item contains `id`, `usedPercent`, `fetchedAt`, `expiresAt`, and nullable `resetsAt`. Reject unknown fields/IDs, wrong source, invalid percentages/timestamps, duplicates, unsupported schema, and payloads exceeding 16 KiB before database writes. An upload with no usable source entries is not sent.
- **Write response and errors:** Follow existing Worker response conventions. A successful PUT returns accepted-row and ignored-old-or-duplicate-row counts. Missing/wrong credentials are 401, invalid input is 400, unsupported media type is 415, oversized input is 413, and throttling is 429 with retry guidance. Validate the whole batch before executing an atomic write. Reuse existing bounded-body parsing, rate-limiting, host/method/query checks, and sanitized request telemetry.
- **Storage:** Add an incremental D1 migration for latest Weekly Allowance Snapshots in the existing database. Maintain one row per fixed provider slot, containing source identity, normalized used percentage, source sampling/expiry/reset timestamps, and server receipt time. Only the configured M4 source may write this resource. Update an existing row only when the incoming `fetchedAt` is newer; equal-time duplicates and older observations are no-ops. Do not use percentage magnitude for ordering, since legitimate resets lower usage. No snapshot history or extra indexes on frequently changing metrics are required.
- **Failed-source behavior:** A missing/invalid individual source resource is omitted from that upload while other valid providers may advance. Keep any last successful stored value under its original sampling and expiry times. A total collection failure never replaces successful data with zeroes. Missing or malformed selected resources must be reported locally; do not infer a login error that the source contract does not expose.
- **Read boundary:** Add authenticated `GET /api/usage-limits` using a separate `X-Usage-Read-Key`. The device receives only that read credential; it must not receive the existing write key. GET returns schema `rcink.usage-limits.v1`, `servedAt`, and exactly four entries ordered `claude`, `codex`, `kimi`, `gemini`. Entries contain `id`, `status`, `usedPercent`, `remainingPercent`, `fetchedAt`, `expiresAt`, and `resetsAt`. Account identifiers, emails, raw source payloads, plans, credits, and provider credentials are not returned. No query or request body is supported. Use `Cache-Control: no-store` rather than the site's anonymous public projection cache.
- **Freshness:** Derive status at read time. A never-observed slot is `unavailable` with null values/timestamps. An observed slot is `stale` once its source expiry is reached or a known reset has passed without a new observation; otherwise it is `ok`. Serve retained values for stale entries. Never make data fresh merely because the Worker received another upload or answered another GET. When a read credential is missing from deployment configuration, fail only the new resource with a service/configuration error, not unrelated site routes.
- **Device transport:** The configured RLCD fetches the new API with certificate and hostname validation, a descriptive application User-Agent, JSON Accept header, a bounded response size, and bounded timeouts. Do not forward its read key to arbitrary redirect targets. Use existing NTP/RTC handling for time validation; an untrustworthy local clock must not cause retained data to be labeled fresh. Preserve the last good cache on transport, authentication, throttling, schema, or parsing failure, and make the failure visible without exposing credentials.
- **Device integration:** Preserve the existing background-network/main-task reconciliation boundary: network work fetches and validates, while the main task updates NVS, RTC, and display state. Reuse the existing Deck/PageRecord/DSL machinery where it fits, retaining per-provider source timestamps in persistent usage state. The old HTTP-fetch-time-only stale check is insufficient for this page. Configure this device to use the usage source; RLCD builds without that setting retain their Axiom behavior, and other firmware targets keep their existing behavior.
- **Display:** Fit all four rows on the 400×300 monochrome panel with existing font/palette primitives. Make remaining percentage prominent; show used percentage and remaining-allowance bars consistently. Identify Gemini as Antigravity, show sampling age/time and source reset information compactly, and mark stale rows individually. Unavailable rows show `--` without a full or empty allowance bar implying a known amount. Persist the selected usage view for startup and retain existing button navigation to the climate Dashboard.
- **Device cadence and offline state:** In usage mode, poll every five minutes while a USB data host is present. Preserve current battery-mode adaptive polling, low-battery handling, button wake, retained display, and deep sleep. Re-evaluate freshness during normal loop/probe wakes even when the network is unavailable, without waking continuously or redrawing unchanged content. Restore source times and values from NVS after restart. Battery operation may therefore show older samples, which must remain visibly labeled.
- **Cost:** The owner accepted five-minute uploads on the current $5 Workers Paid plan. At four rows per upload and 30 days, the baseline is 8,640 upload requests and 34,560 data-row updates monthly. With one device polling at the same rate, total additional Worker requests are 17,280/month. Index maintenance can increase billed row writes; measure actual D1 metrics rather than assuming SQL statement count equals billing. Skip exact duplicate source snapshots, but write new observations even when percentages remain unchanged so freshness stays accurate. Storage remains four latest rows.
- **Rollout:** Build and test against a clean checkout without overwriting unrelated M4 work. Apply the additive database migration, configure the new read secret, deploy the Worker, verify its contract, and then enable the scheduled uploader. Finally verify the connected board identity, back up its firmware, build/flash the RLCD, and perform end-to-end checks. Rollback consists of disabling the new uploader and restoring Worker/firmware versions; the additive table can remain without affecting existing data.

## Testing Decisions

- Prefer tests of externally observable results over private helpers, call counts, generated source layout, or implementation-specific class boundaries. Use deterministic clocks and anonymous realistic source fixtures, not live provider credentials in automated tests.
- **Primary seam: upload/read API behavior.** Reuse Just Ship's existing Worker Vitest/D1 integration environment and migration setup. Exercise the uploader's projection of an OpenUsage v2 fixture through PUT and then GET against real test D1. Assert the resulting four-slot response, authentication, time semantics, persistence, and isolation from the existing heatmap API. Reuse the existing token-write, token-read, routing, and security test patterns; do not introduce a new service framework just for testing.
- At that seam, cover all four mappings; valid zero versus unavailable; multiple-account selection; wrong/missing weekly resources; partial and total source failure; duplicate/older uploads; a newer lower post-reset usage value; expired source data despite fresh receipt/export times; and never-seen slots. The per-provider timestamp must survive the complete round trip.
- Cover the new API's exact bounded schema, unsupported versions, duplicate IDs, invalid/future timestamps, invalid numeric values, absent/wrong keys, read-key write rejection, write-key read rejection, content type, oversized bodies, and atomic rejection. Confirm old token read/write behavior still passes and the existing public cache never contains the private response.
- Keep a small collector-boundary test for helper failure, malformed output, execution/request timeout, overlap protection, account configuration errors, and failed HTTP submission. Reuse the established injected clock/process/HTTP conventions. Verify that the daily collector's schedule and completion behavior remain independent.
- **Device seam: validated API snapshot to visible and persisted usage state.** Reuse RLCD native tests for decoding, layout, navigation, timing, and power-policy logic. Test source expiry and reset transitions while offline, unknown clock state, malformed input, partial availability, restart/cache restoration, and loss of authentication without losing last good values. Verify usage-mode HOST polling without changing the existing battery or non-usage policies.
- **Hardware acceptance:** Compare the M4 CLI snapshot, authenticated GET response, serial state, and decoded real framebuffer. Confirm four correct provider percentages, readable 400×300 layout, startup view, buttons, climate access, and successful certificate-validated HTTPS. Exercise a controlled source outage, device disconnection, and restart; verify truthful stale/unavailable states and retained values. Use fixture-driven automated tests for reset timing rather than waiting for a real weekly reset.
- Run the affected collector and Worker checks, database migrations in the test environment, Cloudflare deployment dry-run, relevant RLCD native tests, and the production firmware build. Test failures or missing live-environment checks must be reported explicitly; issuing this spec is not evidence that these acceptance checks have passed.

## Out of Scope

- Cloudflare Tunnel, a new M4 HTTP server, a second Worker, or a second database.
- Restoring OpenUsage's retired HTTP interface, adding provider integrations, changing OAuth/token refresh behavior, or copying provider credentials to Cloudflare or the device.
- Reusing or modifying the retired stopwatch project.
- Changing the public token heatmap, daily token collection, or representing token totals or dollar spend as subscription allowance.
- Gemini CLI/web usage, non-Gemini Antigravity pools, model-specific Claude limits, Codex Spark/credits, or replacing missing weekly values with daily/monthly limits.
- Percentage aggregation across accounts or machines, an account-switching UI, provider configuration screens, or historical allowance charts.
- A general-purpose dashboard platform, changes to other firmware targets, or redesigning the shared DSL.
- More aggressive battery-mode polling or claims about battery life without measurement.

## Further Notes

- Coordinating issue belongs to [justinyanme/rcink](https://github.com/justinyanme/rcink); backend/collector work also touches [justinyanme/just-ship](https://github.com/justinyanme/just-ship). Treat both as required parts of one complete feature.
- Read-only investigation on 2026-11-09 confirmed all four resources on the M4, with remaining percentages of Claude 50%, Codex 51%, Kimi 96%, and Antigravity Gemini 100%. These are historical evidence, not fixtures to hardcode as current values.
- The inspected source contract has per-provider `fetchedAt`, `expiresAt`, and `stale`, but no top-level error array. The application normally refreshes every five minutes and source snapshots expire after ten minutes. Independent application, upload, and device schedules do not guarantee a five-minute end-to-end freshness bound.
- The running M4 application bundle and the globally installed CLI symlink pointed to different bundles during investigation. Bind the uploader to the verified running bundle's helper; do not assume matching command names imply matching versions or cache domains.
- Just Ship's configured production architecture is Worker + D1, while the M4's token collector runs daily. Investigation found no active token-allowance Tunnel in that chain. Preserve this deployment boundary rather than following historical architecture assumptions.
- Default Python requests received Cloudflare error 1010 during read-only checks; a descriptive application User-Agent succeeded. Include this requirement and validate the actual ESP32 client. See [Cloudflare error 1010 guidance](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/).
- Pricing checked on 2026-11-09: Workers Paid includes 50 million D1 row writes/month, then $1/million; baseline feature data-row writes consume approximately 0.069% of that allowance. Workers includes 10 million requests/month, so the estimated 17,280 requests consume approximately 0.173%. Included quotas are account-wide, CPU/storage/index work is separately relevant, and total account usage was not inspected. See [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) and [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).
- The M4 Just Ship checkout had unrelated uncommitted changes during investigation. Preserve them and reconcile deployment inputs explicitly. Do not turn publishing this specification into an implementation, deployment, credential rotation, or firmware-flashing action.
